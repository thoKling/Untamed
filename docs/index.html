The idea

One system is a penalty. Five are a situation.

A thirst bar on its own is bookkeeping. The goal here is a chain of consequences where every link is a real mechanic, and where the player solves a problem by understanding the loop rather than by watching a meter.

  • Travel in rain
    • →
  • Get wet
    • →
  • Insulation drops
    • →
  • Body cools
    • →
  • Need fire
    • →
  • Torch is exposed
    • →
  • Torch goes out
    • →
  • Need shelter
    • →
  • Build a protected fire
    • →
  • Dry off, warm up

Highlighted links are implemented today. The rest are designed and scheduled, not written.

What exists today

The first slice, end to end.

Milestones 1 and 2 of the brief: the technical foundation, and one complete gameplay slice. Nothing from milestone 3 onward is written yet, deliberately. The brief asks for the first slice to work fully before any of it is started.

Shipping

Rain douses torches

A torch under open sky, in a biome where rain actually falls, has a chance each sweep of going dark. It stops emitting light, the lighting engine reacts, and nearby players hear it hiss.

Shipping

Torches are crafted unlit

Coal and a stick no longer buy light outright. Place the torch and use flint and steel on it, or hold the stack against any open flame to light all of it at once.

Shipping

Relighting is a choice

By default a doused torch stays dark until a player relights it. Only a torch the weather put out can be relit by the weather. One doused on purpose stays dark.

Shipping

A launcher of its own

A desktop launcher installs Minecraft, Fabric, the mod and its dependencies, keeps them current, signs the player in through Microsoft, and starts the game. No manual Fabric install, no dragging jars into a folder.

Designed

Temperature and hydration

Biome and weather driving body temperature, heat driving water consumption. Modelled in the brief, scheduled for milestones 3 and 4.

Designed

Wetness and carry limits

Getting wet, drying out, fire as warmth, and a backpack system that changes how much a player can take with them. Milestones 5 and 6.

How it works

Cheap enough to leave running.

A weather mechanic that scans the world is a mechanic a server operator turns off. Positions enter an index when a chunk loads or a torch is placed, and leave when the chunk unloads or a sweep finds nothing there. 

chunk loads ──► ChunkFireIndexer ──► FireIndex ◄── SurvivalTorchBlock.onPlace
                                        │
              every N ticks             ▼
        WorldFireService.tick ──► FireSweep ──► FireDousingSystem
                                        │              (decides)
                                        ├── MinecraftFireProbe   (reads world)
                                        └── MinecraftFireMutator (writes world)

The world is never scanned

Chunk indexing walks only the chunk sections whose block palette mentions a torch, so a chunk without one is rejected almost for free. Sweeps take a bounded slice and resume where the last one stopped. Clear skies with nothing drying means no sweep at all.

One block, one property

A torch is a single block with a lit property, not two blocks swapped for each other. Light emission is a function of that property, so Minecraft re-lights the area and tells clients on its own. The mod never touches the lighting engine.

Vanilla torches are redirected

A mixin swaps the vanilla torch state at placement time, which covers every route a player has to placing a torch without replacing the vanilla block itself.

Minecraft is the adapter, not the rules.

The dependency direction is strictly downward. domain imports no Minecraft class anywhere, which is what makes the rules testable in about a second without a game instance, and what would make a NeoForge port a rewrite of one layer rather than of the mod.

PackageRoleMay depend on
domainSurvival rules and state. Plain Java.nothing
integrationBlocks, adapters, mixins, config IO.domain
serverLifecycle, scheduling, per-world services.domain, integration
networkPacket definitions and registration.domain
clientHUD, tooltips, rendering.everything above

The client source set is compiled separately and stripped from a dedicated server, so a client-only reference in common code fails at build time instead of crashing a server at runtime.

Configuration

Every number is yours to move.

Written to config/untamed.json on first run. A malformed file is never fatal and never overwritten: defaults are used for that session, so a typo cannot stop a server from booting or destroy a hand-tuned file. Out-of-range values are clamped rather than trusted.

KeyDefaultMeaning
torches.enabledtrueMaster switch for the mechanic
torches.extinguishChance0.35Chance per sweep that a rained-on torch goes out
torches.thunderstormMultiplier2.0Applied to that chance during a thunderstorm
torches.relightWhenDryfalseWhether rain-doused torches relight themselves
torches.checkIntervalTicks40Ticks between sweeps, per world
torches.maxChecksPerInterval512Approximate positions inspected per sweep
torches.convertVanillaPlacementtrueWhether placing a vanilla torch yields the survival torch
Roadmap

Nine milestones, two of them behind us.

The order is deliberate. Each milestone has to work end to end before the next one starts, because the value of these systems is in how they meet, and systems that do not work individually cannot meet well.

  • M1 · DONETechnical foundation Fabric project on Minecraft 26.2 and Java 25, client and server launch, logging, tests, mod metadata.
  • M2 · DONERain and torches Custom torch state, rain detection, sky exposure, lighting updates, placement handling, performance-safe tracking.
  • M3Temperature prototype Player survival state, a temperature value, biome and weather influence, the update loop and its first effects.
  • M4Hydration Hydration state, drinking, water sources, dehydration stages.
  • M5Environmental simulation Wetness and drying, fire as warmth, and the first real interaction between temperature and hydration.
  • M6Inventory and backpacks Limited vanilla inventory, backpack items and storage, persistence, custom UI, networking.
  • M7Client experience The survival HUD, temperature and hydration visualisation, shaders, environmental effects.
  • M8Advanced survival Insulation, clothing, stamina, fatigue, sleep, food spoilage, water purification. Only once the core is stable.
  • M9Balancing and compatibility Polish, tuning, and playing well with the rest of the ecosystem.
Build it

Clone, build, play.

The Gradle wrapper is committed, so no Gradle install is needed. Compilation targets Java 25 through a toolchain, which Gradle resolves from any JDK 25 on the machine. Gradle itself can run on an older JDK. 

./gradlew build           # build the mod jar
./gradlew runClient       # launch a dev client
./gradlew runServer       # launch a dedicated server
./gradlew test            # domain tests, no Minecraft needed
./gradlew -p launcher run # the desktop launcher

No remap step

Minecraft 26.x runs under official mappings directly, so build/libs/untamed-0.1.0.jar is the shippable artifact. There is no Yarn dependency, because Yarn is not published for the 26.x line.

Version coordinates in one place

Every Minecraft, Loader, Fabric API and Loom version is declared in gradle.properties and nowhere else.

Update surfaces are marked

The places where Minecraft's own API has changed shape recently carry a Version-sensitive comment, and all of them sit in the integration and client layers. If a build fails after an update, start there.
